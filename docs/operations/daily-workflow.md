# Well Operations: from programme to reviewed daily log

**API 0.22.0 · schema revision `e2f4c9b71a38`**

Use **Well Operations → Operations Dashboard** for operational time, depth and schedule. **Costing Dashboard** (`/business-dashboard`) still shows the existing AFE and cost figures. Neither dashboard writes to the other module. A plan in Operations is a programme of activities, **not** the costing well plan.

## Work one operating day

1. **Open a rig, then a well.** Plans & timeline, Daily reports and Documents start with rig folders. Records load after the well is opened. Use the scope picker to show drilling, completion or both; Deleted entries also use folders. The well's rig and available drilling/completion scopes come from Rig & Well. The same well can have a different programme and report series for each scope. Operations doesn't need an AFE, daily cost sheet, invoice or cost-access role.
2. **Set the baseline in Plans & timeline.** Create a draft version. Enter activities or preview an Excel timeline/CSV, choose the sheet, check the descriptions, target depths and planned hours, and save in the full-width timeline editor. **Study this timeline** gives a short brief on the activities, planned time, final stated MD and ambiguous or missing checkpoints. Preview and study don't change the plan. Review the total, then activate it. An active version is read-only; activate a new version to supersede it. Only unused draft versions can be deleted and restored. Enter a programme start instant if known, particularly for completion programmes.
3. **File originals in Documents.** Browse by rig → well and filter the scope if needed. Upload, download the original, edit its filing details, or move it to Deleted entries. The vault does **not** create reports. Deduplication is within the workspace, well, scope and document type; retiring a type does not rename existing files. A referenced original cannot be purged while a report still uses it.
4. **Create the report in Daily reports.** Choose **Extract PDF / Excel** to use an already-filed source or upload a new one. For multi-day workbooks select the operating date. Or use **New report** for manual entry. The register's **Import** creates draft *headers*, not time intervals. There is one report per well, scope and date; add a supplemental source from the existing draft instead of creating a second day.
5. **Review against the original.** Extraction opens a full-width draft review; existing draft reports open the same editor. Check source identity, period, depth/units, rotating hours, surveys, the suggested criteria and the evidence. Edit a row to correct it. The criteria are, in this order: **Hole Section, Phase, Sub-Phase, Activity, Allocation, Cause Code, Operations, Agency / Service Vendor, responsible Agency**. Hole Section, Phase, Activity and Agency / Service Vendor come from Master Data; Sub-Phase, Operations, Cause Code and the responsible Agency label are configured in the Code Library. The Activity carries its own type (Planned / UPA / NPT), so choosing it sets the block's Activity type instead of a separate classification field; Hole Section, Phase, Activity and Allocation are always required, and the Cause Code is required only when the Activity is NPT or UPA. Use **Code Library → Default Codes** to read the built-in references and **Correlations** to choose which fields a matching printed token should pre-fill. At least one criterion is required, but no particular field is mandatory: a printed operation can suggest just a Hole Section, for example. A correlation never approves a block. A **Link criteria** rule joins two or more criteria (Hole Section / Phase / Sub-Phase / Activity / Operations / Cause / responsible Agency / vendor / Source mark) and fills a remaining empty field only when every active link agrees; correlation counts beside each value open the rules that use it. Source-mark rules affect new suggestions, not previously saved records. Select a completed programme activity when a depth alone does not identify the checkpoint.
6. **Confirm, save, then submit.** Saving edits is not the same as confirming source review. An authorised reviewer checks the confirmation and saves the reviewed draft. Submission is a separate action and validates overlap, operating period, completeness and NPT requirements. Do not invent time to make a partial report total 24 hours: confirm whether the reported period is genuinely partial or whether rows are missing. A DMR with measurements and no time log can be submitted without inventing a shift. A stale editor must reload rather than overwrite a newer save. Submitted and approved records are read-only; a submitted report can be returned for correction.
7. **Use the results.** The dashboard counts drafts and review work separately. Only current submitted/approved data contributes to time and performance KPIs. Select a well/scope to see its schedule variance. Analytics plots the programme, reported depths, ROP and lead/lag, with report drill-through for readers. The report PDF includes the saved brief, log, survey stations and source names. Deleted drafts can be inspected in their folder, but must be restored before they can be edited. Register exports support CSV, Excel and PDF; in the reports/documents registers checked visible rows take precedence over the whole filtered list.

## What the figures mean

| Figure | Basis |
| --- | --- |
| Operations planned days | Sum of the version's activity hours ÷ 24. Missing target depth is not zero depth. |
| Logged time | Difference between reviewed UTC instants. Reports use the workspace's local operating-day boundary (default midnight, Africa/Lagos). The default two-minute completeness tolerance permits a `23:59` close; it doesn't add a minute to the log. |
| Time categories | **Planned / UPA / NPT** is the **Activity type**, carried by the Master Data Activity. **PT / UPA / NPT / SP** is the separate allocation. Productive time uses the productive flag; the Operations and responsible-agency breakdowns use the NPT allocation. |
| ROP (m/h) | Metres gained ÷ measured rotating hours for the **same** interval. Prefer the report pair, otherwise aggregate complete block pairs. Portfolio ROP is the ratio of the summed pairs, not the average of daily rates. A missing denominator is unknown, not zero or a 24-hour estimate. **ROP is not applicable to completion**, so completion reports, summaries, analytics, the dashboard and every export show `N/A` rather than a drilling-derived number. |
| Actual days | Elapsed time from the saved programme start, or reported drilling days from spud (DFS) when the drilling plan is undated. Relative time from the first submitted period is labelled and cannot establish schedule variance. |
| Lag (days) | Actual days minus planned cumulative days at the confirmed activity, or at an unambiguous interpolated depth. Positive = behind. A plateau or missing basis has no depth-based estimate. A confirmed activity need not have a depth. The saved baseline version controls historical variance even if the active plan changes. |
| Dashed projection | Continuous rotation at the latest positive measured ROP to the next deeper active target. It is not a prediction of total well duration. |
| Missing daily logs | Closed operating days inside a **dated active programme**, not the entire lifetime of every configured well. Seven days by default; at most 31 selected days and 100 displayed gaps. A mud-only report is not a daily time log. |

## Inputs and limits

- Searchable OpenWells daily PDFs (DDR, DCR, RMR): operation summary and survey sections, source page, split/continued narratives, metric/feet headers. A simple `From / To / Activity` text table also has an adapter. The internal header can disagree with the filename. Verify the report date, printed units, event and folder rather than relying on the filename.
- Operations Summary `.xlsx`/`.xlsm`: select the operating day, not the whole workbook's history. Table-based workbooks with start, end and activity columns can also be read. DMR sheets contribute measurements, partial surveys and a summary, not inferred activity hours. Attached DMRs do not replace an existing time log. The source files are kept byte-for-byte; workbook formulas are not executed and read-only adapters use cached results.
- Plan imports accept a supported programme table (including the supplied four timelines), or CSV with `description`, `planned_hours` and optional `target_depth_m`. Preview is limited to 10 MB and a saved timeline to 2,000 activities. Scanned PDFs have no OCR here. Encrypted, legacy binary Excel and unrecognised layouts need a readable export or manual entry; filing a supporting file does not guarantee it can be extracted.
- Extraction and study are deterministic by default. The daily brief identifies the work described, time balance, measured depth and rotating ROP when supported by the measurements. The timeline study uses planned values only; it does not generate speeds or actual checkpoints. The broader [design plan](implementation-plan.md) is not a list of shipped features.

### Deleting and restoring

Code library rows, correlations, multi-criteria code links, plans, reports and documents all follow the same two-step rule. **Delete** moves a live record to **Deleted entries** (it disappears from pickers and extraction, and history keeps its recorded values); **Restore** brings it back; **Delete permanently** is offered only inside Deleted entries, asks for explicit confirmation, and is refused while a report block, programme item, active rule or other operational record still references the code. A code referenced by an active correlation or code link cannot even be soft-deleted until that rule is removed — the refusal names the rule, and the rule count beside the code links straight to it.

## Code references and offline AI

**Default Codes** separates the definitions printed in the engineers’ workbook (activity, programme phase, operation, Plan/trouble and cause codes) from OpenWells phase tokens and observed uses of the numeric `Code` column. The supplied PDFs don't include a vendor dictionary, and the two sources don't always use the same number for the same work. For example, workbook Activity `06` is *Wiper trip and reaming*; OpenWells `06` is also seen on other trips. Workbook `02` is *Rig moves*, but in the PDFs `02` is used in drill-ahead and tool rig-down narratives. Review the narrative, not just the number. Printed tokens remain visible even if no definition is known. Nothing in the default catalogue seeds rigs, wells, agencies or vendors.

Under **Brief & report details** or **Timeline study**, **Use offline AI** is off by default. Enabling it checks the existing [LAN Ollama configuration](../ollama-ai.md); generating the narrative sends bounded qualitative notes from the rule-based study to that configured model. Numeric KPIs stay in the unchanged brief. A model that responds but cannot produce usable wording is distinguished from a failed connection. The wording is displayed separately, not saved as the report or used for calculations. If Ollama is disabled or unavailable, keep using the deterministic brief. **Well Operations → Ask & guide**, or the contextual Guide drawer, explains workflows, code families and calculations under your role's permissions.

## Well path, dogleg and diagram

**One well, three questions.** *Where was the hole drilled?* — the surveyed trajectory. *What has been installed?* — the casing schematic. *Where was the tool or string?* — the report snapshot. The three are drawn from separate records and are never used as evidence for one another.

- **Two linked 2D projections.** Plan view means looking down, with north up and an equal north/east scale; it is not "planned well". Vertical section is the shadow of the path on a vertical plane facing the stated bearing, so motion out of that plane disappears. Selecting a station in either projection highlights it in the other, in the schematic and in the station table. A station selected from the table, a bar or the keyboard opens the same source drawer, because the drawer receives a station or interval identity rather than a chart pixel.
- **Severity belongs to an interval.** `DLS = dogleg × 30 / L` between two stations, from the angle between the two 3D tangent directions. The first accepted station has no interval and therefore no severity (`— no interval`); a straight pair is a genuine `0`. The reported/typed rate is carried as a separate mark and compared, never substituted. An interval whose endpoints cannot be trusted (repeated MD, out-of-range angle, near-opposed directions) is listed for review rather than plotted as a number. A printed rate in °/100 ft is converted with `30 / 30.48`.
- **Construction and trajectory use different axes.** The casing schematic is drawn on measured depth; the integrated path is drawn on true vertical depth. They are labelled separately and a casing seat is never converted into a TVD. A recorded shoe with no recorded top gets a wedge and a label; a configured interval is design, not installed casing. Below the last known shoe the drawing says *casing coverage unknown* unless the record supports open hole. No liner, cement, tubing, packer or total depth is fabricated.
- **Three positions, kept apart.** The **marker** is the selected report's closing measured depth (preferring a verified report). The **survey endpoint** is the deepest accepted station. Any hole below it is annotated as unsurveyed — never drawn as a continuation of the last tangent. The **snapshot** is the report's own bit/string depth; off-bottom distance is arithmetic only when both figures come from the same report, datum and bore, otherwise the page says *not comparable*. Missing is not surface, and "out of hole" needs an explicit observation.
- **Anchor basis is stated.** A first station with a printed TVD/N/E anchors the curve to the record; without one the curve is tied on at surface level with zero departure and the page says so. A missing azimuth on a deviated station is not replaced with north: that station is excluded and named in the notes.
- **Source drawer.** Every mark offers *Explain this*: the recorded values and their report, date, status and page; the calculated values and the formula with its numbers; the configured values; and what the record does not contain. Facts are tagged recorded / calculated / configured / missing.
- **Depth window and export.** *Window from/to* clips the plots only, never the record, and the caption states the window. *Fit well* restores the whole well. Statistics, the station table and every export use the full resolution.

## Deployment and permissions

Back up the database, deploy the backend with its locked parser dependencies, run `alembic upgrade head`, then deploy the matching frontend. Revision `c1d9e5a4f702` follows `b4d621f389aa`. It adds printed code provenance and rounds existing decimal columns to three places in Operations **and costing**. The figures already stored in historical snapshots are rounded, not repriced. Check a representative reconciliation after migration. The migration stops before conversion if a positive legacy FX rate, required invoice quantity/day count or payment split percentage below `0.0005` would become zero. Review those records with Finance; do not substitute a guessed or default rate. A downgrade restores the old column scale and drops the new provenance fields, but **cannot recover discarded digits**. Restore the backup if those digits are needed.

Use User Management for deliberate assignments. New capabilities `ops-dashboard:read`, `ops-doc:export`, `ops-plan:import`, `ops-plan:restore` and `ops-master:restore` are provisioned for existing owners, **not** silently granted to custom roles. Do not give an Operations user costing rights just to populate a well or vendor selector. The dashboard doesn't require `ops-report:read` to show totals, but it does require it to return the recent report details. Original download, extraction, review, submission, approval, report printing and register export have separate capabilities. Extraction into a new report requires document read/extract and report read/create; adding a source requires document read/extract and report read/update. Upload is only needed to add a new file.
