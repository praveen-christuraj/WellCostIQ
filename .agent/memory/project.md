## Entry checks on the daily cost sheet: values that look mistyped (2026-11-13)

- **Origin.** First group built from a proposal for assistance that fits the hosting plan: point out values on a daily cost sheet that look mistyped, explain why, and offer the correction. Using no model, adding no dependency and never blocking a save are design decisions taken on the measurements below, not requirements handed down; revisit them only with new measurements.
- **Three rules that must not be broken.** (1) Advice only: a finding never blocks a save or a submission and never changes a figure by itself; `checks_for_preview` never raises and returns `[]` on any failure. (2) Explainable and deterministic: every finding quotes its figures and its basis; no randomness, no clock inside the rules. (3) Standard library only: do not add numpy, scikit-learn, LightGBM or a language model for this. Measured on the 512 MB host budget: the API idles at about 140 MB, LightGBM with its numeric stack adds about 230 MB on disk and about 43 MB resident on import.
- **Layers.** `backend/app/domain/entry_statistics.py` (pure: `build_profile`, `measure`, `far_from_median`, `explain_slip`, `explain_slip_in_sum`; all thresholds are named constants at the top) → `backend/app/domain/entry_rules.py` (pure: `LineFact`/`SheetFacts`/`Plan`/`History`, one `check_*` per rule, `evaluate`) → `backend/app/services/entry_checks.py` (queries, workspace profiles, reviews, the five entry points). Keep the split: rules never touch the database, the service never decides what is unusual.
- **Method.** History = the nearest `ENTRY_CHECK_HISTORY_SHEETS` (30) other sheets of the same AFE and well; an item needs 5 values, otherwise its workspace profile (`daily_cost_item_profiles`, rebuilt from the ledger after the response, never adjusted in place). Profile = median + spread on a log scale; spread = max(1.4826 × MAD, trimmed range ÷ expected range), floor 0.12, widened for short histories. Note at ≥ 2.5× and ≥ 3.5 spreads; warning when a keying slip explains it (≥ 4 spreads) or at ≥ 5× and ≥ 6 spreads. Slips tried: ×10/×100/×1000, doubled digit, swapped digits, hours ↔ days, feet ↔ metres, inverted exchange rate. Single references (locked rate, AFE estimate rate) use plain ratios: 3× note, slip or 20× warning.
- **Findings** (`code`): `unusual-quantity`, `more-than-a-day`, `unusual-rate`, `unusual-fx`, `fx-inconsistent`, `unusual-sheet-fx`, `depth-outside-plan`, `depth-decreased`, `depth-ahead`, `duplicate-line`, `usual-line-missing`, `unusual-day-total`. A finding has a stable `key` and a `fingerprint` of the exact value judged.
- **Reviews.** "Keep as entered" stores one typed row in `daily_cost_check_reviews` (key + fingerprint + what was kept + note + who/when). Only a finding the *saved* sheet still carries with that fingerprint can be reviewed (409 otherwise), Draft sheets only (409), audited as `update` on `daily_cost`. A changed value no longer matches the fingerprint, so the finding is open again.
- **API.** Preview gains `entry_checks`; `GET /daily-cost/entries/{id}/checks`, `GET /daily-cost/wells/{well_id}/checks` (`daily-cost:read`); `POST .../checks/review`, `POST .../checks/reopen` (`daily-cost:update`). **No new capability.** API contract **`0.10.0`** (`backend/app/main.py` + `frontend/src/lib/api.ts`).
- **Migration `b7d3e9f25a41`** (follows `a2c5d8f14b30`): creates `daily_cost_check_reviews` and `daily_cost_item_profiles`; no existing row changes; upgrade → downgrade → upgrade verified on SQLite and PostgreSQL 16.
- **Settings** (`core/config.py`, `.env.example`, `docker-compose.yml`, `render.yaml`, `docs/deployment.md`): `ENTRY_CHECKS_ENABLED`, `ENTRY_CHECK_HISTORY_SHEETS`, `ENTRY_CHECK_PROFILE_WINDOW_DAYS`, `ENTRY_CHECK_PROFILE_MAX_AGE_HOURS`. With the switch off the API answers `enabled: false` and the UI renders nothing.
- **UI.** `components/daily-cost/EntryChecksPanel.tsx` on `pages/DailyCostSheet.tsx` (above the Services table): tags *N to check / N to note / N kept as entered / Nothing unusual*, **Apply** (edits the unsaved payload only, via `lib/entryChecks.ts` `applyEntryCheck`, which refuses a suggestion that no longer matches the line), **Keep as entered** (`FormDialog`, saved Draft only), **Reopen**; actions are disabled while the findings are stale. `components/daily-cost/WellEntryChecksCard.tsx` on `pages/DailyCostAnalysis.tsx` lists the sheets of the well with open checks. The Submit dialog names open checks without blocking. Guide memory entry `entry-checks` (`SYSTEM_MEMORY` now has 22 entries).
- **Measured limits, stated in `docs/entry-checks.md`.** `make entry-checks-simulation` (seeded, about a minute) prints two tables: detection/false alarms by spread and history size, and how often an offered correction is the intended value. Rerun it and update the document whenever a threshold or slip rule changes. Order-of-magnitude slips on steady items: always caught, always corrected exactly. Items varying ±30%: ×10 flagged 56% with 5 earlier values, 93% with 8; corrections exact. Items that double or halve: corrections 90-96% exact; items varying by several times: 50-85%, because the history cannot identify the power of ten. Correct values flagged: 0-0.3% (0.55% worst case). Not caught: anything inside the usual range (one wrong digit, most swapped digits). **Known weakness:** a doubled or swapped digit, or any unlisted mistake, on a varying item can receive a decimal-point reading (`112.3` offered for `1123` where `123` was meant; within 10% of the truth in about 9 cases in 10 for doubled digits). Four alternative selection rules were simulated (prefer the digit reading when the decimal reading needs a new decimal place; no suggestion when both fit; posterior weighting with a confidence threshold of 0.60 and of 0.75) and each lost more correct suggestions than it removed wrong ones under equal slip frequencies, so "most frequent slip first" stands. The real mix of slip types is unknown: revisit with the review table (`daily_cost_check_reviews`) and applied suggestions once real data exists.
- **Cost.** A preview takes about 30-60 ms longer in the sandbox (9-25%; reading about 1,900 neighbouring lines); peak extra memory about 4.5 MB per preview and 24 MB for a 120-sheet well review. The early exit `far_from_median` / `rules.unremarkable` (a value within 2.5× of the median can never be a finding) is what keeps the well review fast; do not replace it with a cache.
- **Verification.** `backend/tests/test_entry_checks.py` (28 tests: statistics, rules, API success/failure/isolation, migration by revision) on SQLite and PostgreSQL; `make entry-checks-check` (jsdom, 19 groups; the section and the well card are rendered under both themes and must show the same words and actions); full backend suite, `npx tsc -b`, `npm run build`, `npm run test:security`, `bandit -r backend/app -l`.
- **Lessons.** (1) A save copies every exchange rate entered on a sheet line into `daily_cost_baseline_exchange_rates` (`_upsert_lines`, `extra_rates`), so that table can already hold the very value being judged and cannot be the reference for an exchange-rate check; `afe_exchange_rates` (the estimate, which no daily sheet changes) is. The baseline table is only used to convert amounts. (2) A wrong exchange rate must not also raise a rate finding: `check_exchange_rates` returns the doubted (currency, rate) pairs and `check_rates` skips comparisons through them. (3) `alembic check` already reports drift on unrelated tables on `main`; judge a new revision by whether *its* tables appear in that output. (4) A pytest run imports the application once: code edited while the full suite runs is not covered by that run. (5) In jsdom a MUI dialog stays in the DOM for its closing transition: asserting that it is gone 100 ms after Cancel fails and 200 ms passes, so the check waits 350 ms; and a button lookup by label must be scoped to its panel (the sheet has its own **Reopen**). (6) `npm ci` enforces `engines` (`>=22.23.4 <23`); use that Node rather than editing `engines` or `.npmrc`.
- **Not started.** The other groups of the same proposal were only mapped in the code, not built: likely-duplicate vendors (`api/vendor_master.py` `_duplicate_vendor`), duplicate invoices (`services/invoice_processing.py`), and the fuel, mud and dashboard figures (`services/fuel_cost.py`, `mud_cost.py`, `business_dashboard.py`). Each is a separate increment; the statistics in `domain/entry_statistics.py` are reusable for them.

## In-application guide: constant memory plus computed answers (2026-11-13)

- **User directive.** The application needs an assistant that explains how it works and answers questions about the workspace's own figures, and that cannot make things up. It must be trustworthy for an operator on day one, usable from any page, and correctable by the workspace.
- **Two sources, never a model.** `backend/app/services/assistant.py` answers from (1) `SYSTEM_MEMORY` — 22 shipped entries, 21 from this increment plus `entry-checks` (`workflow-*`, `calc-*`, `entry-*`, `nav-*`, `policy-*`) seeded idempotently into `assistant_memory` per workspace, quoted verbatim; and (2) figures computed by the same services the pages use (`daily_cost.progress_overview`, `well_cost_summary`, AFE balances, `data_checks`). **There is no model call anywhere**, so a question always produces the same, auditable answer and a number can always be traced to its register. Unknown questions return `confidence="low"` plus the list of topics it does know; it never guesses a figure.
- **The answer contract** (`schemas/assistant.py`): short prose + `facts[]` (`label`, `value`, `hint`, `route`, `permission`) + `steps[]` + `sources[]` (page routes) + `follow_ups[]`; `intent` is one of `knowledge | data_health | actual_days | cost_position | forecast | out_of_scope | npt_upa | status | permission`. Intents are keyword-classified (`INTENT_RULES`) with two guards learned from the tests: (a) an *explanation* question ("how are actual days calculated?") routes to memory even when it names a figure, unless it also says "how many/how much" or names a record code (`_asks_for_explanation`); (b) memory scoring uses only curated `keywords` and the title — never the prose body — with a stopword list, because scoring bodies made "who won the world cup?" match every entry containing "the".
- **Permissions decide both the figures and the answer.** Everything is computed under the caller's capabilities: a caller without `daily-cost:read` gets `intent="permission"` naming the exact key instead of a number, and `data_checks` only covers modules the caller may read. `assistant:read` opens the guide; `assistant:manage` (owners) writes workspace memory. Shipped memory is immutable by design — `update/delete` raise for `is_system` rows and surface as **409**, not 403, because the caller does hold `assistant:manage`.
- **Workspace memory is quoted the same way.** A workspace records its own rule (title, category, keywords, body, steps, route, optional required capability); it is matched, answered and cited identically, is audited (`create/update/delete` on `assistant_memory`) and is never visible to another workspace (`memory_key` unique per organisation).
- **Privacy.** The transcript (`assistant_conversations`) is per user and per workspace: the history endpoint returns only the caller's own questions.
- **Migration `a2c5d8f14b30`** (follows `e1b4f7a92c35`) creates `assistant_memory` + `assistant_conversations`, grants `assistant:read` to every existing role and `assistant:manage` to owners; upgrade → downgrade → upgrade verified on SQLite.
- **UI.** `pages/Assistant.tsx` (*Help & Guide → Ask the guide*, route `/assistant`, guard `assistant:read`) shows the ask box, the answer card, outstanding data checks with the page that fixes each, the caller's recent questions, and a *Memory* tab listing shipped and workspace entries with add/edit/remove for `assistant:manage`. `components/assistant/AssistantLauncher.tsx` opens the same service in a drawer from any page (floating button, `Alt+G`), passing the current route so that page's memory ranks first. Both render through `components/assistant/AnswerCard.tsx`, so there is no second, weaker assistant.
- **Verification.** `backend/tests/test_assistant.py` (6 tests: seeding idempotency, memory-backed answers with routes, unknown-question fallback, viewer permission gating incl. 403 on memory create, workspace memory create/answer/isolation against a second organisation, shipped-memory 409 and per-user transcript), `.agent/tools/assistant-check.jsx` (`make assistant-check`, 23 jsdom assertions: sentence verbatim, figures with their guarding capability, steps, proving pages, follow-up buttons, refusal styled as a refusal, unknown labelled, no markup injection, quick prompts), `npx tsc -b --noEmit`, `npm run build`, the 47 UI checks and the full backend suite. ## Well status and plan status ladders, one-step rollback (2026-11-13)

- **User directive.** Well statuses are **Upcoming → Active → Final review → Completed**; plan statuses are **Draft → Configured → Completed**. Every transition is consistent in every module, can move forward and can be **rolled back one step** to the previous status. Before this, "final review" was a *plan* status while "completed" was a *well* status, so a well in final review still read as Active and each module re-derived its own gate.
- **One state machine: `backend/app/services/well_lifecycle.py`.** Nothing else may compare status strings to decide what is allowed. Per configuration scope (Drilling / Completion, independent): `configure` draft→configured (needs saved sections), `draft` configured→draft, `start` upcoming→active (needs a Configured plan), `defer` active→upcoming (409 while the scope has daily cost sheets or a recorded spud; AFEs do not block), `final_review` active→final_review (plan closes as Completed), `reactivate` final_review→active (plan back to Configured), `complete` final_review→completed (409 while any daily sheet of the scope is Draft), `reopen` completed→final_review. No move skips a step; the old `activate` action is gone. Public API: `TRANSITIONS`, `available_transitions(well, scope, can)`, `apply_transition(...)`, `auto_start`, `reset_scope`, `accepts_planning`, `planning_blocker(well, scope, purpose)`, `STATUS_LABELS`, `PLAN_LABELS`.
- **Coupling, enforced by the database too.** A scope in Final review or Completed always has a Completed plan and an Upcoming/Active scope never does (`ck_wells_status_plan`, `ck_wells_completion_status_plan`). Fixtures that insert a `Well(status="completed")` directly must also set `config_status="completed"`.
- **Roll-ups** (`models/rig_well.py` `rolled_up_status` / `rolled_up_plan`, exposed as `Well.tracking_status` / `Well.tracking_plan_status`): Completed only when every live scope is completed, Upcoming only when every live scope is upcoming, Final review when every live scope is in final review or completed, otherwise Active. Plan roll-up covers open scopes only (Configured if any is, else Draft; Completed when no open scope remains). Registers, the overview cards, the Business Dashboard, usage-report filters, Mud/LIH references all use these — never the Drilling columns alone.
- **Permissions.** Forward moves need `rig-well:update`; every rollback needs the new **`rig-well:rollback`** and is audited with action `rollback` (forward moves stay `update`). Remarks of at least 3 characters are mandatory for every move. Migration grants `rig-well:rollback` to the owner role and to every role that already held `rig-well:update` (they could reopen/defer/reactivate before), so nobody loses authority; administrators then remove it from forward-only roles.
- **Migration `e1b4f7a92c35`** (follows `d7e3a91c4f60`): active + plan final_review → status final_review + plan completed; upcoming + plan final_review → plan configured; status completed → plan completed; recreates the CHECKs with the new vocabularies plus the two coupling CHECKs; typed SQLAlchemy table expressions for the permission backfill (the PostgreSQL `AmbiguousParameter` lesson). Downgrade restores the old vocabulary. Upgrade → downgrade → upgrade runs inside `tests/test_well_lifecycle.py`.
- **API contract `0.8.0`.** `WellOut.drilling_transitions` / `completion_transitions` and `WellConfigurationOut.transitions` list every move that starts at the scope's current state (`action`, `label`, `description`, `ladder`, `direction`, `to_status`, `to_plan`, `permission`, `permitted`, `allowed`, `reason`). `POST /rig-well/wells/{id}/transition {action, scope, remarks}`: unknown action 422, missing permission 403 (names the capability), other workspace 404, wrong state 409 with what to do first. `GET /rig-well/wells` accepts `status=upcoming|active|final_review|completed`, `config_status=draft|configured|completed`, optional `scope`; the overview returns `upcoming_wells`, `active_wells`, `final_review_wells`, `completed_wells`, `draft_wells`, `configured_wells`.
- **Cross-module rule: a scope takes new work only while Upcoming or Active on a Configured plan.** New daily sheet: 409 in Final review/Completed, 422 while the plan is Draft; the first sheet still auto-starts an Upcoming scope. AFE create 422, estimate save and submit 409. Plan save 409 unless Draft. Well plan adjustment and AFE SOW adjustment create/approve 409 (void always allowed). **Daily sheets stay editable in Final review** (that is when they are corrected and submitted) and are **frozen once the scope is Completed** — save, date change, reopen, import, delete, restore and their bulk forms return 409 until the scope is rolled back to Final review. Submit and permanent delete are deliberately not frozen. A scope that is re-added after deletion starts again at Upcoming / Draft.
- **UI.** `lib/rigWell.ts` (`WellStatus`, `PlanStatus`, `trackingLabel`, `planLabel`, tones, `isOpenWellStatus`, `scopeTransitions`, `wellTrackingStatus`) and `components/WellLifecycle.tsx` (`WellStatusTag`, `PlanStatusTag`, `WellTransitionDialog`) are the only place the wording and tones live. `Wells.tsx` has one tab per well status and a **Status** menu grouped "Move forward" / "Roll back one step": the menu renders exactly the server's options, shows a blocked move disabled with the server's reason, and hides a move the user is not permitted to make (`permitted === false`). The same dialog confirms forward moves and rollbacks, showing before → after on both ladders. AFE and Daily Cost registers have "Wells in final review" and "Completed wells" tabs driven by the scope's well status. ## One-dialog Day Rate scope configuration (2026-11-12)

- **User directive.** A Day Rate service could only carry one rate card on one section, so a service whose cost differed per section had to be entered once per section. It must be configured once: every section and phase of the well in the *same* dialog, each with its own rate (and optional own days), the service amount being the sum of those section amounts. Duplicate entries of the same service must be clubbed, and both the AFE estimate report and the Daily Cost report must print a service once per section, phase, activity and sub-activity.
- **Engine** (`domain/afe_costing.py`): `ServiceRateInput(category, unit_rate, section_id, phase_id)` and `ScopeDaysInput(category, quantity, unit, section_id, phase_id)` join `ServiceLine.service_rates` / `.scope_days`. Pricing order per day category and scope: scope rate → shared rate on a scoped line → shared rate split across sections by planned days (the unchanged legacy behaviour) → legacy `rates`. Every category is priced **exactly once per scope**, so sections never double count; a rate for a whole section covers only the phases of that section that carry no phase rate of their own (`_scope_days_or_free_phases`), which is the case a naive implementation double-counts; one-time categories (Mobilization, Demobilization, Fixed Charge) are charged once per scope rate row, or once well-level. `scope_days` beats the well plan for that scope only, and hours still convert at 24/day.
- **Storage** (`models/afe.py`, `models/sow_adjustment.py`, migration `d7e3a91c4f60` following `c4d5e6f7a8b9`): `afe_service_scope_rates` (unique line+section+phase+category) and `afe_service_scope_days`, mirrored as `afe_sow_service_scope_rates` / `afe_sow_service_scope_days` for SOW revisions. Plain child rows, no JSON. Upgrade/downgrade/re-upgrade verified on SQLite plus `tests/test_bootstrap.py`.
- **API** (`schemas/afe.py`, `services/afe.py`): `ServiceLineIn.scope_rates[]` / `.scope_days[]` (bounded, `Decimal10`), `ServiceLineOut.scope_rates[]`, `.scope_days[]` and `.scopes[]`; `RService` carries the same tuples plus the resolved `scopes` list, so one line still prices once and reports every scope it covers. Validation rejects a duplicate (section, phase, category), an unknown scope, a one-time category given days, and hours above 24; the client checks mirror it.
- **Daily cost clubbing** (`services/daily_cost.py`): a line configured by scope fans out to **one locked allowance per priced (section, phase)** (`item_key` gets a stable `~<sha1>` suffix, `_service_budgets_for` / `_budget_for_scope`), and `_service_rate_snapshots` freezes one rate row per scope, so `_normalise_service` matches the actual to the allowance **of its own scope** (`_budget_for_scope`, section-only allowances still resolve). `_comparison` now carries `hole_section_id`/`section_label`/`phase_id`/`phase_label`/`club_count` and `_club_scoped_service_rows` sums every planned allowance of one service in the same (section, phase, group) into a single printed row — unbudgeted actuals keep their own key. Legacy single-scope lines keep their untouched `service:<line id>` key and amounts, which is why the whole existing suite stays green.
- **UI**: `ServiceLineDialog.tsx` gains the section/phase rate matrix (add, edit, remove, own days; the well-wide card remains for a shared rate), the editor list shows the scope and rate counts, `AfePrintSheet.basisDetail` prints one detail row per section and phase under the service's single row, and `SowAdjustmentDialog.serviceOutToInput` carries the scope rows. `serviceProblems()` accepts a section-only rate card and rejects duplicate scope rates. No client-side price maths: the server still owns every amount.

## Reusable templates, bulk price revision and the rig-scoped register (2026-11-12)

## “Not found”, capability-aware security centre, readable errors (2026-10-30, later)
- **Where “Not found” came from.** The API's 404 pass-through handler forwarded FastAPI's bare detail and `api.ts` rendered whatever arrived, so an unmatched route (`{"detail":"Not Found"}`) or a record-level 404 reached the user as two words with no context. Three layers now prevent it: the server rewrites route-level 404/405/401 defaults into a sentence naming the method, path and `API_VERSION` (and logs the unmatched call); `scoped()` raises *“That user account is not in this workspace…”*; and `lib/api.ts` drops known-useless details in favour of a sentence that includes the failed action. Optional/background calls pass `{ silent: true }` (bell poll, print companions) so they never raise the pop-up at all.
- **Unknown addresses are a page, not a redirect.** `pages/NotFound.tsx` shows the requested path, the usual reason (an older page bundle than the deployed build), Reload, Back and Dashboard actions. It replaces the catch-all `<Navigate to="/" replace/>`, which had made a dead bookmark look like a silent landing.
- **Validation messages are translated.** `api.ts` maps FastAPI's structured 422 items to sentences a user can act on (`string_too_short`, `string_pattern_mismatch` → “must be one of: low, normal, high, critical”, `too_short` on a list, numeric/date/bool parsing, `missing`, `extra_forbidden`). Unknown shapes fall back to `msg`, so a new server rule is never blank.
- **The security centre follows the capability that opened it.** `security:password-reset` alone now reaches `GET /security/overview` and the recovery queue through `deps.require_any`, which is what lets a reset reviewer who cannot read the account register still clear requests; the register, bulk actions and lock/unlock keep their own capabilities, and the page asks only for what the viewer may read (queue-only reviewers see the tab, an explanatory banner and no 403s). Navigation and the route guard use the same three capabilities.
- **Self-target actions are explained instead of failing.** The API refuses force-change, session revocation and lock on the caller's own account (409); those buttons are now disabled with the reason, an owner account cannot be locked by a non-owner, and a deactivated account cannot receive a reset code. Bulk selections containing the caller say so, because the API skips them.
- **Task comments follow the same rule as the API.** The comment box in the task panel is only rendered when the task reports `can_manage`; a viewer who can read a task but not act on it sees a sentence instead of a box that would fail.
- **`require()` names the capability it needs** (`"Permission denied. This action needs security:read."`), and the bulk endpoint does the same. `lib/uiEvents.ts` keeps the header badge and the notification centre in step through a `notifications-changed` event, with a quiet reload that avoids flashing the table spinner.

## Standing product conventions (mandatory for every module and page)
These are cross-cutting requirements. Every new page, module, and feature must comply; code review must reject violations. They apply to User Management, Master Data Management, Business modules, Report modules, Back-up modules, Auditing modules, and anything added later.

1. **Audit everything.** All user actions on all pages (create, update, delete, assign, import, export, sign-in/out, admin changes) are written to the audit trail with actor, action, entity, summary, IP and timestamp. Audit records are read-only to normal users. Every page ships with auditing by default.
2. **Light and dark themes.** Every screen must work in both Light and Dark themes, with matched font colours, borders, backgrounds and chart/grid palettes. The user selects the theme (persisted per browser); defaults to the system preference.
3. **Collapsible side navigation.** Primary navigation is a permission-aware left rail grouped by module. It expands to labelled module/page lists, collapses to icon buttons with accessible tooltips and menus, persists the desktop preference per browser, and becomes a temporary drawer below the desktop breakpoint. The slim top bar is contextual only (current module/page, theme and account); it must not duplicate the primary links.
4. **No JSON in the database.** Never store JSON/JSONB blobs, serialized documents, or key-value payload columns. Use conventional, typed, column-wise table design (one column per business attribute). API responses may shape JSON; persistence must not.
5. **Pagination everywhere lists appear.** Every page listing data uses pagination with page-size options **20 / 50 / 100** (default 20), both on server-driven lists and in grids.
6. **Easy and advanced filtering.** List pages offer a quick (easy) search plus an advanced filter panel that can filter on any available column/criterion (equals, contains, ranges, etc.). Date and date-range filters are kept as a separate, dedicated control group (from/to pickers), distinct from the general filters.
7. **Import and export.** Data list pages provide import from Excel-family files (**.xlsx and .csv**) and export to **.xlsx, .csv and PDF**, with preview before import and row-level errors shown inline. (Endpoints/pages that cannot support import must at least support export.)
8. **Module-wise dashboards.** Each module (User Management, Master Data Management, Business modules, Report modules, Back-up modules, Auditing modules, …) gets its own dashboard/summary page showing module KPIs and recent activity. Modules are still being added; do not represent unbuilt modules as shipped.
9. **Navy Blue & White enterprise theme.** Professional Navy Blue and White palette (light) and navy-based dark palette; no green branding, no unnecessary animations, no decorative motion, no emojis. Enterprise-grade, business-oriented, well-structured layouts.
10. **Alerts near the data plus clear error pop-ups.** Field errors remain beside the responsible input and destructive actions confirm via dialog. Failed API actions also show one persistent top-right error pop-up with the server's actionable message (or a clear permission/not-found/conflict/server/network fallback), so failure is visible even when the affected control is below the fold. Do not use detached page banners or `window.alert`.
11. **RBAC on every page.** Every page is created with RBAC controls by default; visible actions are permission-gated and the admin user controls access through roles/permissions. The API remains the authorization authority.
12. **Pop-ups close only via Cancel.** Any data-entry pop-up (create/edit/assign/delete confirmation, import, change password, and any future dialog) must NOT close when the user clicks outside it (backdrop) or presses Escape, and has no X/close icon. Only the **Cancel** button closes it (a successful save/import also closes it). Implemented once in `FormDialog` (`frontend/src/components/Common.tsx`), which `ImportDialog` and all pop-ups reuse; do not pass `onClose` to a raw MUI `Dialog` or add backdrop/Escape close handlers. Panels that are not a single submit form (the PO/SO attachments and revision-history panel) use `PanelDialog` from the same file, which enforces the same rule with a footer button instead of a submit action.
13. **Per-record actions and bulk selection.** Every mutable master-data/business-record row exposes Edit and Delete actions for users authorized to use them; data tables include a checkbox per row and a header checkbox to select all matching entries for bulk actions. Gate each action by RBAC and keep immutable/security-protected identity and RBAC records subject to their existing safeguards.
14. **Soft delete first; purge only from Deleted Entries.** A normal Delete action on master/business data must soft-delete the record and move it to a Deleted Entries view. Never permanently delete an active master/business record. Restore and permanent-delete actions are offered from Deleted Entries; permanent deletion requires an explicit confirmation dialog. Audit soft delete, restore, and permanent deletion.
15. **Never lose entered data — unsaved-changes protection everywhere (2026-10-13).** Every data-entry surface must protect what the user typed before it disappears. This is mandatory for every existing page and every future module. (a) Pop-ups: `FormDialog` (`frontend/src/components/Common.tsx`) detects any input in the dialog (typing, option picks, toggle changes; pages may also pass an exact `dirty` prop, computed with `useFormDirty`) and, when the user clicks Cancel, asks first: "Save & close" runs the dialog's normal save path (a validation failure keeps the dialog open with the messages next to the fields), "Discard changes" closes deliberately, "Continue editing" stays. Confirmation-only dialogs (no inputs) are never dirty and keep their simple Cancel. (b) Full-page editors (AFE estimate, daily cost sheet, and every future entry page) call `useUnsavedChangesGuard({ when, onSave })` from `Common.tsx`, which intercepts in-app navigation and the back button (React Router `useBlocker`, which is why `main.tsx` uses `createBrowserRouter`) and tab close/reload (`beforeunload`), offering "Save & continue" / "Discard changes" / "Continue editing". Reuse these two primitives; do not hand-roll new close guards. (c) A workspace default currency (`currencies.is_default`, exactly one active default per workspace, set from Master Data → Currency) is preloaded by every currency dropdown: `MasterSelect` preloads it for new priced records, and the AFE reference payload carries `is_default` so AFE line dialogs, the bulk estimate and the standard-currency picker start from it. Keep these behaviours intact when adding modules.

- Navigation is the collapsible permission-aware side rail in `frontend/src/components/Layout.tsx`; it persists expanded/collapsed state, uses a drawer on smaller screens, and retains module menus in icon-only mode. The contextual top bar holds only the current module/page, theme toggle and account menu.
- Design tokens are centralized in `frontend/src/designSystem.ts` (navy ramp, surfaces, semantics, type scale, spacing, radii, shadows, motion, AG Grid skin), composed into `theme.ts` and mirrored as `--wcp-*` variables in `styles.css`. Pages must not hardcode colours, radii or font stacks; status chips read the CSS variables because AG Grid cell renderers may not receive the React theme context. See `.agent/memory/design-system.md`.
- `frontend/src/components/DataTable.tsx` is the standard list surface: quick search, advanced filters (per-column rules + separate date & date-range group), AG Grid pagination 20/50/100, and Export (CSV/XLSX/PDF) via `frontend/src/lib/export.ts`. `frontend/src/components/ImportDialog.tsx` is the standard import flow (xlsx/csv parse, preview, row-level errors).
- FastAPI + SQLAlchemy 2 + Alembic; PostgreSQL for Compose/deployment, SQLite only for lightweight local development and tests.
- Organization IDs scope all RBAC and audit records; never accept an organization ID in a management request. Authentication uses workspace slug + email + password.
- Access JWT stays in browser memory; rotating opaque refresh tokens are hashed in DB and sent as HttpOnly SameSite cookies. A password change revokes sessions and increments token version.
- API is the authorization authority. Client-side `can()` only hides controls. Owner role is immutable and assigned only by provisioning to prevent lockout. Nonowners cannot grant access they don't have.
- Capability keys use `resource:action`; baseline API capabilities are provisioned per organization, and custom capabilities are tenant data. Baseline includes `audit:read` for the Other Managements audit log and `database-browser:read`/`database-browser:export` for the Database Browser.
- **Audit trail is column-wise** (`audit_logs` table: actor, action, entity_type, entity_id, entity_label, summary, ip_address, user_agent, created_at — never a JSON payload column). `app/services/audit.py` records entries in the same transaction as the change; `app/api/audit.py` serves the paginated, filterable `/audit` list behind `audit:read`.
- **Master Data Management** is an organization-scoped module with five typed tables (`uom`, `currencies`, `phases`, `hole_sections`, `activities`), shared lifecycle timestamps, per-workspace unique codes, and `is_deleted`/`deleted_at` soft-delete fields. `/api/v1/master-data` maps those typed attributes to a common API record shape; its dashboard, tabs, Deleted Entries view, row actions, and bulk actions follow this app's MUI/AG Grid structure, not the legacy UI. The `master-data:*` capabilities guard reads, writes, restore, purge, import, and export; migrations backfill those permissions for existing owners. Permanent deletion is accepted only for already soft-deleted rows. Every module action is written to the typed audit trail.
- **Services** are a typed register within Master Data Management (`app/models/service_master.py`, `app/api/service_master.py`, `frontend/src/pages/Services.tsx`). `services` stores a workspace-unique manually entered code (trimmed and upper-cased), service name, category (Drilling Services or Completion Services), provider type (In House Services or Third Party Services), vendor FK, description, and common soft-delete/audit lifecycle columns. Service names are case-insensitively unique per workspace, including deleted rows; both provider types require a non-deleted workspace vendor on create/update/import/restore. Historical unassigned in-house services remain readable until explicitly assigned; no vendor is invented during migration. The service dashboard summarizes categories and provider types; list actions use the shared import preview, filtering, pagination, and CSV/XLSX/PDF export. Imports require service_code and vendor_code, upsert/restore by code, accept legacy Inhouse/3rd Party labels and default old rows without a category to Drilling Services. Vendors referenced by active services cannot be soft-deleted; service assignments must be purged before their vendor can be purged. The API reuses the `master-data:*` capabilities and includes Services in the Master Data overview and Deleted Entries page.
- **Vendors and PO/SO Orders** are the commercial tabs of Master Data Management (`app/models/vendor_master.py`, `app/api/vendor_master.py`, `frontend/src/pages/Vendors.tsx`, `frontend/src/pages/PoSoOrders.tsx`). Vendors are added first (`vendors`: code unique per workspace, vendor type (Inhouse or Third party), category, contact, e-mail, phone, website, country, tax/registration no., address, status active/inactive/blocked, credit terms; the category list includes Completions beside Drilling); a blocked vendor is refused new orders, and a vendor with active orders or active Services cannot be soft-deleted or purged until those records go. Orders (`po_so_orders`) carry **no prices or values** — the attached scan is the record. Each order number forms an amendment chain: revision 0 is the original, `parent_order_id` + `revision_number` (server-assigned) hold the lineage, `is_current` marks the revision to quote, and renaming an order number renames the whole chain. Documents (`po_so_documents`) store several files per revision with kind/label/notes, SHA-256 checksum (duplicates inside one order are refused), uploader, and the revision they were attached to; removal is soft (recoverable from the same panel) and only purge is permanent. Bulk attach matches `<ORDER NUMBER>[_Rev<N>].pdf` file names to orders.
- **Attachments live in the workspace database** (`po_so_documents.content`, a deferred `LargeBinary`, capped by `DOCUMENT_MAX_SIZE_MB`, default 15) because the deployed API filesystem is ephemeral. This is a binary payload, not a JSON document, so the column-wise rule still holds; every other attribute is a typed column. Moving to object storage later means swapping `_store_document`/`download_document` only.
- **Document custody is separately grantable**: `master-data:document-upload`, `master-data:document-download`, `master-data:document-delete` join the existing `master-data:*` capabilities (provisioned for new workspaces, backfilled to owners by the vendors migration). Downloads are audited too, so the trail shows who opened which PO/SO copy.
- Migrations are explicit Alembic revisions. Do not use `create_all` in the app runtime.
- The owner account is the platform administrator. On a new device the database is empty, so at startup the API detects the missing owner and asks the operator to create one (`app/bootstrap.py` + prompts in `app/services/console.py`, provisioning in `app/services/provisioning.py`, schema state in `app/core/migrations.py`). It never invents credentials, never writes to an existing tenant, never creates tables behind Alembic and never blocks a non-interactive process; `SEED_*` variables cover unattended first boots and `BOOTSTRAP_ADMIN_ON_STARTUP=false` disables the check. `python -m app.seed` is the same flow as a CLI, `--check` exits 0 admin present / 1 missing / 2 unmigrated / 3 failed.

- **Column-wise by design.** `daily_cost_entries` (header: rig/well/AFE snapshots, cost date, status, remarks, group totals, UPA/NPT totals, warning count, soft delete) plus four typed line tables (`daily_cost_service_lines`, `daily_cost_consumable_lines`, `daily_cost_tangible_lines`, `daily_cost_other_expense_lines`). - **Rate immutability is the core rule.** A daily sheet prices only from its baseline snapshot or a justified per-line `override_rate` + `override_reason`. Later Master Data revisions never flow backwards into an existing sheet.
- **PostgreSQL row locks must stay single-table (production 503 fix).** Every daily-cost write locks a row, and the models load several many-to-one references with `lazy="joined"`. Locking an entity-shaped (or eager-loading) SELECT therefore emits `LEFT OUTER JOIN … FOR UPDATE`, which PostgreSQL refuses with `FOR UPDATE cannot be applied to the nullable side of an outer join` (SQLSTATE 0A000) — every `POST /daily-cost/entries`, save, submit, reopen, delete and restore answered 503 while SQLite (which ignores the clause) kept the suite green. `_lock_row_id(db, model, *criteria)` now locks `model.id` only — single-table by construction, whatever loader strategies the models declare — and the row is then read with its usual eager loading in the same transaction (`_get_entry`, `_ensure_rate_baseline`/`_rate_baseline_by_id`, `_ensure_afe_baseline`/`_baseline_for`). The same rule applies to every module: never add `joinedload`/`lazy="joined"` to a row-locked statement, and prefer the lock-the-key-then-load shape.
- **PostgreSQL GROUP BY is strict.** The whole-well budget reconciliation selected `activity_name`/`party_name` while grouping only by `(cost_group, budget_key)` (SQLite picks an arbitrary bare row; PostgreSQL raises `GroupingError`, so `GET /daily-cost/wells/{id}/cost-summary` returned 500). The labels are now `func.min(...)` aggregates, keeping one deterministic name per budget key on both dialects.
- **500 hardening.** `import_daily_cost()` normalises `charging_basis` through `BASIS_ALIASES` (case-insensitive `day rate`/`dayrate`/`day`/`per service rate`/… ) and validates the quantity unit, instead of indexing raw strings; `_flush()` and `_commit()` map `IntegrityError`→409, `DataError`→422 and other SQLAlchemy/database failures→503 with rollback and logging; baseline races reuse the winning immutable snapshot where possible; create/save/read-back boundaries turn malformed legacy AFE data into actionable 422/503 responses; `reference_data()` skips unusable AFEs instead of failing; `_money()` raises 422 past `MONEY_LIMIT = 9999999999999999.99` (mirrors Numeric(18,2)). `app/main.py` adds a JSON `http_error` handler and a global `unexpected_error` handler that logs the traceback and returns 500 with a short `reference` id; the daily-cost 503 detail now carries the same kind of reference (`[xxxxxxxxxxxx]` in `Daily cost <operation> failed with a database error`), so a user report can be matched to the exact failing statement in the Render logs. Net effect: daily-cost create/edit database and data-boundary failures are no longer leaked as opaque 5xx responses.
- **Pricing and operator guardrails.** Day Rate `Mobilization`, `Demobilization` and `Fixed Charge` lines are unit-priced events: the positive recorded quantity is retained for operations, but the selected rate is charged exactly once. The day-sheet grid and line dialog show the same semantics. - **Entry rules: Activity-derived classification, mandatory well sub activity, split services.** Classification (Planned/UPA/NPT) is **not** entered on a daily cost line — the Master Data Activity already serves that job. `classify_activity()` (`app/services/daily_cost.py`) derives it from the activity code/name (NPT / non-productive → NPT, UPA / unplanned → UPA, else Planned; mirrored in the frontend by `deriveClassification()` in `lib/dailyCost.ts`), and it is stored on each priced line so `upa_total`/`npt_total`, warnings and the Planned/UPA/NPT analysis factor keep working. `classification` is removed from the line input schemas (extra keys are rejected) and from the import template; a legacy `classification` column in imported files is ignored. Configuring the well sub activity in Rig & Well Management is mandatory for daily cost entry: `create_entry` rejects a well with no active sub activities (message points at Rig & Well Management), and every service/consumable/tangible line must carry a `sub_activity_id` belonging to the well and the selected Activity (`_get_sub_activity` is non-optional). On the same date for the same well, the same service may be recorded multiple times **only** under different sub activities (e.g. 18h/3h/3h across sub activities); `_reject_duplicate_service_sub_activity()` rejects a repeated service + sub activity pair on save/preview/import. The day-sheet grid shows a SUB ACTIVITY column (the entry CLASS column was removed), and the line dialog enforces mandatory sub activity, no-duplicate-service, and UPA/NPT party/manual-rate rules (driven by the derived classification) next to the fields; the register's create dialog blocks wells without configured sub activities.
- **Other expenses (LIH and similar) are a fourth cost group that is deducted from the AFE (2026-10-13, user requirement).** Unexpected charges — Lost In Hole, hole problems, fishing/recovery, side track, equipment damage, third-party claims, penalties, misc — are captured in `daily_cost_other_expense_lines` instead of being smuggled into Services/Consumables/Tangibles. The user's three explicit decisions: (1) its own cost group whose total **is** part of the day's cost, with AFE reconciliation `Total AFE − (Services+Consumables+Tangibles) − Other Expenses = remaining`; (2) a **fixed picklist** of expense types (no master-data register, no free-text category — the deduction rule depends on the type and an open list would let a mis-typed category change the AFE position; each row snapshots `expense_type_label` and keeps optional free text in `expense_description`); (3) the amount is **quantity × entered unit rate** in the line currency, converted with the locked AFE FX like every other line (no catalogue lookup and no `override_rate` — a daily override is meaningless where there is no baseline rate, so the schema rejects it and `rate_source = other_expense`). **Remarks are mandatory** (>= 3 non-blank chars, `OTHER_EXPENSE_MIN_REMARKS`) because the remark is the only narrative explaining the charge; enforced twice — in the Pydantic input validator *and* as `CHECK (LENGTH(TRIM(remarks)) > 0)` on the table — because the API is not the only writer. The lines still carry the full operational scope (Phase, Activity, Sub-Activity, Hole Section, vendor/party) and derive Planned/UPA/NPT from the Activity as usual, so they classify, filter, group and audit identically; `planned` for the group is always 0.00 and `budget_key = other:<TYPE>` makes the expense type the reconciliation row. Import accepts `Line Type = Other` with spoken aliases (`OTHER_EXPENSE_TYPE_ALIASES`, `lost in hole` → `LIH`); missing remarks/rate or an unknown type are row errors, never a 500. ## Backup & Recovery and Report Builder / Custom Reports (2026-10-30)

Ported from the `hydrocarbon-accounting-otms` reference (its `REPORT_BUILDER.md` / `BACKUP_OPERATIONS.md`) into this stack — SQLAlchemy models and Alembic instead of raw Postgres tooling, the shared `DataTable`/`FormDialog`/`PageHeading` layer instead of its bespoke screens. Every addition is new files plus additive route/nav/capability entries; no existing module, payload or workflow changed.

### Backup & Recovery (`/other-management/backup` and `GET /backup/*`)
- **Six tables** (`models/backup.py`, migration `e8c3a1f75d24`): `backup_settings` (one per workspace), `backup_jobs`, `backup_job_tables` (per-table row counts), `backup_restore_requests`, `backup_validations`, and the audit-linked hold columns on a job. Anonymous archive names never leak the schema: files live under `BACKUP_DIRECTORY/<workspace-slug>/`.
- **What an archive holds.** `services/backup.py` derives the plan from the live metadata: scope `full` covers every table that can be tied to the workspace (directly by `organization_id` or through an FK chain), scope `workspace` narrows it; rows are exported to JSONL with a manifest (schema fingerprint, per-table counts, checksum). Secrets are never written — password/secret/token/hash columns are excluded from the plan, the same rule the Database Browser applies.
- **Actions, all audited and capability-gated:** create a backup (`backup:create`, one running job per workspace via `ensure_no_job_running`), list/filter history, per-table detail, verify against the SHA-256 recorded at creation (`checksum_mismatch` is a real state, not an error text), download (`backup:download`), delete (`backup:delete`, 204), import a previously downloaded archive with multipart field `file` (`backup:create`), retention cleanup honouring `retention_days` / `keep_minimum` / holds / live restore requests (`cleanup`, also exposed as a dry run), and the settings form (`backup:settings`: schedule, retention, keep-minimum, folder name, verification).
- **Scheduling.** `calculate_next_run` plus a startup scheduler thread (`backup_scheduler_enabled`, off in tests) that executes due jobs; `GET /backup/overview` returns `completed`, `latest_completed_at`, storage totals and warnings for the Overview card, and `GET /backup/readiness` lists content-dependent warnings (no completed archive, policy never exercised, etc.).
- **Restore is a two-person workflow.** Request (`backup:restore-request`, reason + target backup) → review/approve or reject (`backup:restore-approve`) → cancel (requester) → **validate** into a disposable SQLite database (checksum, schema fit, and a savepoint dry run that is always rolled back) → execute (`backup:restore-execute`) only after approval and a successful validation, with the typed phrase `RESTORE <backup_number>`, an automatic pre-restore safety backup, and a single-transaction row replacement per the reference's operational rules. Validations are listed per request, so the reviewer sees exactly what was checked.
- **Frontend** (`pages/BackupRecovery.tsx`, `lib/backup.ts`): KPI strip from `/overview`, Settings dialog, Archives table (verify/download/delete/import/request-restore), Restore-requests table with the approve/reject/validate/execute buttons each hidden behind its capability, plus a readiness card. Downloads and archive imports use `downloadFile`/`uploadFiles(..., field='file')` because `api()` is JSON-only. The Other Management overview gains a `backup:read` card and the nav entry is `BackupOutlined`.

### Report Builder (`/reports/builder`) and Custom Reports (`/reports/custom`)
- **Nine tables** (`models/report_builder.py`): definitions (design JSON + visibility + owner), grants, versions (immutable published snapshots), and the run/export audit rows. Publishing writes a version and flips visibility; `POST /definitions/{id}/duplicate` and `create_from_starter` cover the reference's "start from a proven design" path (seven starters).
- **The six steps are the schema.** Data + date basis → columns (plain, calculated, comparison duplicates) → rows/layout (`detail` or `grouped`/`matrix`) → run-time filters → visibility + grants (`private`/`internal`/`public`, `everyone`/`roles`/`users`) → live preview, then Save draft or Publish. `ReportDesign` is a strict model, so old draft shapes (`GROUPED`, `everyone`, legacy operators) are rejected rather than silently accepted.
- **Formula engine** (`services/report_formula.py`) is Decimal-only with `[key]` references, right-associative `^`, blanks propagate, `%` means percent-of, and DIV/0 yields a warning instead of a number. `POST /formula/validate` and `GET /formula-help` drive the designer's inline help; problems come back as `{valid, problems[]}` and are shown next to the step that owns them.
- **Execution** (`services/report_engine.py` + `report_catalog.py` + `report_store.py`) re-validates the stored design against the *live* catalogue on every save, preview and run — a column whose table/column disappeared fails with a sentence, never a 500. Row/date filters, grouped totals and matrix pivots are built as SQL; date-range exclusion stays SQL-side (`stats["excluded_by_date"]`), COUNT over zero rows is `"0"` not blank, and comparison columns blank per column key. Caps mirror the reference: 50,000 rows per run (`SCAN_CAP`/`EXPORT_CAP`), 60 columns (60 matrix columns), 30 filters / 12 run-time filters / 100 conditions, page size 500 and a 25 s budget, with `warnings`/`notes` returned alongside the data.
- **Readers.** `GET /my-reports` lists only what is published to the caller (visibility, grants, ownership); `/my-reports/{id}/run` returns `ReportRun` (`columns[{key,label,align}]`, `rows`, `totals`, `total_rows`, `pages`, `page`, `grouped`, `matrix`, `warnings`, `notes`, `stats`, `generated_at`). `export.csv` streams every matching row; XLSX/PDF are generated client-side from the same run (`all_rows`), and `POST /export-audit` records each one. `CustomReportViewer.tsx` auto-runs on open, then re-runs on filter/date/search/paging changes; `CustomReports.tsx` is the published-report gallery.
- **Visibility rules.** Designers hold `report-builder:{read,create,update,delete,publish}`; readers hold `custom-reports:{read,export}`. Secret-bearing tables (`token_blacklist`, `auth_login_challenges`, anything password/hash shaped) are absent from the catalogue entirely, not merely hidden in the UI. `GuardAny` gates the routes and the nav entries (`TuneRounded` Report Builder, `AssessmentOutlined` Custom Reports) so a reader-only account sees the gallery but not the designer.
